# 广告净化器 · 可行性评估与建议

> 状态：孵化中（评估版）
> 评估日期：2025-XX-XX
> 目标用户：本人（个人工具定位）

---

## 0. 一句话结论

**总体可行，但高度依赖"拦截点"的选择；"监测并提前拦截广告"这一核心思路需要重构为"基于规则的实时过滤"，否则项目会在最难的环节卡死。建议从网页端（浏览器扩展）切入做 MVP，手机 App 端只做"现实可行范围内"的过滤（DNS/本地 VPN），不要追逐"覆盖各大平台"的伪目标。**

## 1. 需求还原

| 项 | 内容 |
|---|---|
| 痛点 | 浏览视频 App / 短视频平台时广告干扰 |
| 核心需求 | 过滤广告（拦截广告请求、隐藏广告内容） |
| 目标用户 | 本人（个人自用） |
| 现状 | 思路为"UI 选择开关 → JSON 配置 → 监测视频平台 → 提前拦截" |

---

## 2. 初步思路拆解与纠偏

| 原思路环节 | 评估 | 纠偏建议 |
|---|---|---|
| ① UI 界面让用户选择是否拦截广告 | 合理但优先级低 | 拦截应默认开启，开关只是锦上添花；不是核心难点 |
| ② JSON 保留数据 | 合理且简单 | 配置持久化，任何技术栈都能做 |
| ③ 监测视频平台 | **定义模糊，方向有误** | 需要明确"监测什么"：网络层（流量）还是渲染层（DOM/视图）。真正该做的是"规则匹配"，不是"监测" |
| ④ 提前拦截广告 | **最大误区** | 广告**无法可靠预测**，只能实时过滤——在广告请求发出前/到达播放器前拦截，或渲染后隐藏。不存在"提前拦截"这一操作 |

**核心认知修正：** 广告拦截的本质是"**在合适的位置实时过滤**"，而非"预测并提前拦截"。拦截点的选择（DNS / HTTP / 渲染层）决定了整个方案的可行性和难度，是项目的第一决策点。

## 3. 五大技术路线对比

### A. 浏览器扩展（uBlock Origin 模式）—— 推荐起点

- **原理**：`webRequest` API 拦截 HTTP 请求 + 内容脚本隐藏 DOM 广告元素
- **适用**：网页版视频平台（B站网页、YouTube、爱奇艺网页等）
- **难度**：★☆☆☆☆（有成熟开源生态，甚至可直接复用 uBlock Origin 的过滤引擎）
- **隐私**：全部本地处理，风险低
- **局限**：只覆盖浏览器内，不覆盖手机 App；广告与内容同源域名时请求过滤失效，需 DOM 隐藏兜底
- **注意**：Chrome 正因 Manifest V3 逐步禁用 uBlock Origin（[The Verge](https://www.theverge.com/2024/10/15/24270981/google-chrome-ublock-origin-phaseout-manifest-v3-ad-blocker)、[TechSpot](https://www.techspot.com/news/105130-google-purging-ad-blocking-extension-ublock-origin-chrome.html)），做扩展需考虑 MV3 限制（declarativeNetRequest）或优先面向 Firefox / Edge（仍支持 webRequest）

### B. DNS 级过滤（AdGuard Home / Pi-hole / hosts）

- **原理**：拦截广告域名解析，广告请求在源头失效
- **适用**：所有联网设备（含手机 App 内第三方广告 SDK）
- **难度**：★★☆☆☆（配置现成工具）
- **局限**：**广告与内容共用 CDN/域名的平台完全无效**——国内视频/短视频平台普遍如此（广告主内容与视频内容同源下发），只能拦掉第三方广告 SDK 的域名请求

### C. 本地 VPN（Android 上 AdGuard / Blokada 模式）

- **原理**：本地 VPN 接管流量 → 代理层按规则过滤
- **适用**：Android 手机 App
- **难度**：★★★☆☆（Android 无障碍，可参考 AdGuard 开源实现 [AdGuard 知识库](https://kb.adguard.com/kb/zh-CN/adguard-for-android/installation/)）
- **局限**：同 B——URL 级过滤对同源广告失效；HTTPS 下只能看域名看不到内容（[VPN 型广告拦截器对比](https://deepwiki.com/liuzq2002/Adguard-Home-For-Magisk-Mod/9.5-vs-vpn-based-ad-blockers)）
- **iOS 说明**：只能走 Network Extension VPN，且 iOS 本地 VPN 无法解密 HTTPS，自研价值极低

### D. HTTPS 中间人代理（MITM）—— 不推荐

- **原理**：安装根证书 → 解密 HTTPS → 内容级识别广告并剔除
- **难度**：★★★★★（需对抗证书固定、App 加固、协议频繁变更，是与大厂安全团队的军备竞赛）
- **风险**：**高危**——主流 App 普遍证书固定，代理即被识别或拒绝；明文解密用户全部流量，隐私风险大；违反平台 ToS
- **结论**：个人项目不可持续，直接排除

### E. 修改版客户端（ReVanced / 第三方客户端模式）—— 学习可、产品不可

- **原理**：逆向 App，patch 掉广告逻辑
- **难度**：★★★★☆（国内主流 App 有梆梆、腾讯乐固等加固，逆向成本极高）
- **法律风险**：中高（修改他人软件）
- **结论**：作为个人学习有价值，不作为本项目的产品路线

### 路线速查表

| 路线 | 覆盖端 | 难度 | 隐私风险 | 对"抖音/快手类同源广告"效果 | 推荐度 |
|---|---|---|---|---|---|
| A 浏览器扩展 | 网页 | ★ | 低 | 部分（DOM 隐藏兜底） | ★★★★★ |
| B DNS 过滤 | 全网 | ★★ | 低 | 差 | ★★★★ |
| C 本地 VPN | Android App | ★★★ | 中 | 差 | ★★★ |
| D HTTPS MITM | 全端 | ★★★★★ | 高 | 好但不可持续 | ☆ |
| E 修改客户端 | 单 App | ★★★★ | 低 | 好 | ★★（仅学习） |

## 4. 分平台可行性

| 目标 | 可行性 | 理由 |
|---|---|---|
| 网页版视频平台（B站/YouTube/爱奇艺网页） | **高** | 浏览器扩展生态成熟，规则列表可复用 |
| Android 手机 App | **中** | 本地 VPN 可行，但广告主内容（同源）难过滤，只能拦 SDK 广告 |
| iOS 手机 App | **低** | 系统限制多，自研成本收益比极差，直接建议用户用现成方案 |
| "覆盖各大平台" | **低** | 每个平台都是军备竞赛，个人维护不可持续 |

## 5. 隐私问题评估

- 用户的担忧成立：任何流量层面的拦截（B/C/D）都会看到用户全部或部分网络行为
- **底线原则：本地处理，零云上报**。个人自用场景下隐私风险可控
- 最小化设计：只记录"匹配到的广告请求"日志，不记录完整流量
- 若未来考虑分发：需符合中国《个人信息保护法》（PIPL）等合规要求，复杂度显著上升——这也是建议"个人工具定位"的原因之一

## 6. 建议

### 6.1 重构产品概念
从"监测视频平台并提前拦截广告"改为"**基于规则的实时广告过滤**"。两个字之差，把项目从"研究难题"拉回"工程实现"。

### 6.2 不要从零造轮子
- 规则直接用开源列表：EasyList / EasyPrivacy 等
- 浏览器扩展：复用 uBlock Origin 的过滤引擎（已组件化），或直接给用户配置现成扩展
- DNS 级：直接用 AdGuard Home / Pi-hole
- Android VPN：参考 AdGuard / Blokada 开源实现

### 6.3 MVP 路径（建议）
1. **第一步（1~2 周）**：浏览器扩展原型，锁定单一平台（如 B站网页版），实现"请求过滤 + DOM 隐藏 + JSON 配置开关"，出可用原型
2. **第二步**：接入 EasyList 规则订阅，扩展覆盖多个网页平台
3. **第三步（可选）**：评估 Android 本地 VPN 方案；iOS 端直接引导用户使用 AdGuard 等现成工具
4. **收尾**：写清"已知边界"文档（哪些广告拦不住、为什么），管理预期

### 6.4 预期管理
- 抖音/快手等 App 内广告，现实可行的拦截手段很少（同源下发），**期望值要低**
- 项目定位：**个人学习项目 / 个人工具**，不是要战胜大厂广告系统的产品
- 维护成本真实存在：平台改动 → 规则失效 → 需要跟进更新

## 7. 技术初判修正

| 原判断 | 修正 |
|---|---|
| 基础框架容易构建 | ✅ 正确（UI + JSON 确实简单） |
| 监测识别并提前拦截广告难度偏高 | ⚠️ 部分正确——难的是"选对拦截点"；"提前拦截"本身不可行，实时过滤可行 |
| 存在用户隐私问题 | ✅ 成立，但本地化处理可缓解，个人自用风险可控 |

---

## 8. 最终结论

- **总体可行性：中高，且高度依赖平台选择**
- 网页端（浏览器扩展）：**高可行**，生态成熟，建议作为孵化起点
- Android 端：中等可行，效果有限
- iOS 端：低可行，建议用现成工具替代自研
- **"提前拦截"目标：不可行，必须重构**
- 建议孵化方向：**个人工具定位 + 网页端 MVP + 规则引擎架构 + 本地优先设计**
初代使用结果偏弱，过滤不了软广，但能过滤80%的硬广

# 微信沉浸阅读助手（WeChat Reading Assistant）

> 状态：待孵化 → 已定范围，可进入 MVP 开发
> 平台：**Android 单平台** ｜ 目标应用：**仅微信** ｜ 回复方式：**打字** ｜ 目的：**自用 + 简历项目**

---

## 1. 一句话定位

在微信内沉浸阅读（公众号文章/聊天记录长页）时收到新消息，用一个**悬浮球 + 紧凑回复面板**完成打字回复，发送后**自动返回原阅读位置**，把"切走页面"的干扰降到最低。

## 2. 核心用户故事

```
作为：微信重度阅读用户
场景：正在读一篇长公众号文章，微信来了消息
现状：点横幅 → 切到聊天 → 回复 → 返回文章（阅读节奏被打断）
期望：文章页面上方出现小气泡 → 点开弹出半透明回复面板 → 打字发送
     → 面板收起，气泡消失，文章原位置还在，全程"几乎无感"
```

## 3. 关键设计决策（先读这个）

| 决策点 | 结论 | 理由 |
|---|---|---|
| 植入插件（Xposed/改包） | ❌ 否决 | iOS 不可行；安卓违反微信协议、有封号+法律风险（腾讯诉群控外挂判赔 260 万） |
| 外部悬浮窗辅助应用 | ✅ 采用 | `TYPE_APPLICATION_OVERLAY` 可叠加在任何应用（含微信）之上，无需碰微信 |
| 发送方式 | 无障碍注入（切走→输入→发送→自动返回） | 微信 RemoteInput 快速回复支持不稳定，第三方无法触发别的 app 的 RemoteInput |
| 前台检测 | 无障碍服务事件为主，`UsageStatsManager` 兜底 | 无障碍本来就为发送而开启，顺带获得实时前台检测 |
| 原位返回 | 依赖微信自身的返回栈 + 一次 `GLOBAL_ACTION_BACK` | 微信文章 webview 在返回栈中保留位置；需实测验证（见 §9） |

## 4. 总体架构

```
┌─────────────────────────── 微信（不修改） ───────────────────────────┐
│  公众号文章页（前台）         来消息 → 系统通知（横幅/通知栏）          │
└──────────────────────────────────┬───────────────────────────────────┘
                                   │
        ┌──────────────────────────┼───────────────────────────┐
        ▼                          ▼                           ▼
┌────────────────┐      ┌──────────────────┐      ┌──────────────────────┐
│ ① 通知监听服务  │      │ ② 悬浮窗服务      │      │ ③ 无障碍服务          │
│ Notification-  │──触发→│ TYPE_APPLICATION-│      │ AccessibilityService  │
│ ListenerService│      │ OVERLAY          │      │                      │
│ 解析微信消息    │      │ 悬浮球/回复面板   │←操作─│ 前台检测(微信?)       │
└────────────────┘      └────────┬─────────┘      │ 定位输入框/发送按钮    │
                                 │ 用户点"发送"    │ 注入文本/点击/返回    │
                                 ▼                └──────────┬───────────┘
                        ┌──────────────────┐                 │
                        │ ④ 微信聊天操作器   │◄────────────────┘
                        │ ChatOperator     │（唯一与微信 UI 打交道的模块）
                        └──────────────────┘
```

四个 Android 系统级组件，全部公开 API，不改微信一行代码：

| 组件 | 系统能力 | 职责 |
|---|---|---|
| ① `NotificationListenerService` | 通知监听 | 实时捕获微信通知（延迟 <1s），解析发信人/消息内容，过滤噪音（如"你收到了一条消息"） |
| ② 悬浮窗服务（前台 Service） | `SYSTEM_ALERT_WINDOW` | 挂载悬浮球与回复面板；面板半透明、贴边、适配键盘 |
| ③ `AccessibilityService` | 无障碍 | 实时前台检测（是否在微信）；执行"切走→注入→返回" |
| ④ `WeChatChatOperator` | 无障碍节点 API | 定位聊天输入框（`EditText` 节点）、`ACTION_SET_TEXT` 注入文本、找"发送"按钮 `ACTION_CLICK`、`GLOBAL_ACTION_BACK` 返回 |

## 5. 核心流程时序（发送链路）

```
[来消息] 微信通知出现
   → ① 通知监听捕获 → 解析 → 通知 ②
   → ② 判断前台是微信（询问 ③）→ 是 → 显示悬浮球
[用户点悬浮球] → 弹出回复面板（含消息摘要 + 输入框 + 发送按钮）
[用户打字点发送]
   → ② 收起面板 → 请求 ③ 执行发送：
       a. 通过通知的 contentIntent 启动对应聊天页（不依赖自己拼跳转参数）
       b. 节点查找：className == "android.widget.EditText"（微信聊天输入框）
       c. ACTION_SET_TEXT 注入文本
       d. 查找"发送"节点（text/content-desc == "发送"）→ ACTION_CLICK
       e. 等待消息上屏（轮询最后一个节点或固定延时）→ GLOBAL_ACTION_BACK
   → 回到文章页（微信返回栈保留原位置）
[气泡消失 / 本次回复结束]
```

**"几乎无感"的三个关键点：**
1. 悬浮球只在"微信在前台 + 有消息"时出现，不打扰其他场景；
2. 面板紧凑贴边、半透明，键盘弹出后不遮挡文章主体；
3. 发送后自动返回，用户看到的是"点一下→打几个字→又回到文章"，而不是手动切来切去。

## 6. 模块与代码骨架（建议包结构）

```
app/
├── MainActivity.kt            # 权限引导页（悬浮窗/通知使用权/无障碍/电池白名单）
├── service/
│   ├── WeChatNotificationListener.kt   # ① 通知监听
│   ├── ReplyOverlayService.kt          # ② 悬浮窗（悬浮球 + 回复面板）
│   └── WeChatAccessibilityService.kt   # ③ 无障碍（前台检测 + 执行发送）
├── core/
│   ├── NotificationParser.kt   # 微信通知解析（单聊/群聊、去噪音、会话去重）
│   ├── WeChatChatOperator.kt   # ④ 唯一接触微信 UI 的模块（注入/发送/返回）
│   └── ForegroundDetector.kt   # 前台检测（无障碍优先，UsageStats 兜底）
└── ui/
    ├── BubbleView.kt           # 悬浮球
    └── ReplyPanelView.kt       # 回复面板（含键盘 insets 适配）
```

技术选型：**Kotlin + 单 Activity**（悬浮窗/服务为主，界面很轻，不引入 Compose 也能做；`minSdk 26` 起用 `TYPE_APPLICATION_OVERLAY`）。不依赖第三方大库，核心全是系统 API——简历上讲得清楚，维护也简单。

## 7. 已知的坑与对策

| 坑 | 对策 |
|---|---|
| 微信 UI 节点随版本变化（输入框/发送按钮 id 不稳定） | 用 className + text/content-desc 多策略查找；找不到节点时**兜底**：切到聊天页并提示用户手动发送 |
| 国内 ROM 权限矩阵（MIUI/EMUI/ColorOS 的悬浮窗、自启动、省电策略各不相同） | MainActivity 做引导页 + 检测脚本；自用场景只覆盖主力机 ROM |
| 悬浮球误触/遮挡阅读 | 贴边半透明、长按拖动、无操作自动隐藏 |
| 通知解析噪音（群聊@、折叠通知、公众号推送） | 解析器白名单策略：只处理"单聊/群聊会话类"通知，公众号推送不弹球 |
| 键盘弹出顶起布局 | 面板 `adjustResize` + `WindowInsets` 适配 |
| 无障碍服务被系统/用户关闭 | 服务断开时自动收起悬浮球，引导页提示重开 |

## 8. 合规边界（自用+简历也要写清楚）

- ✅ 使用范围：通知监听、悬浮窗、无障碍（均为安卓公开能力，用途与核心功能直接相关）；
- ✅ 数据全部本地处理，不采集、不上传；
- ❌ 不做：Xposed/Root 注入、改包、Hook、模拟抢红包类操作；
- 说明：无障碍注入"替用户发消息"属于灰色地带，**自用无风险，若将来上 Google Play 需按政策提交声明**（Play 对无障碍服务审核很严，不少开发者因此被拒）。简历里把"对合规边界的判断"写进去是加分项。

## 9. MVP 里程碑（约 4–6 周，自用节奏）

| 阶段 | 内容 | 验证点 |
|---|---|---|
| M0（1 周） | 先做 3 个**事实验证**（见下） | 任一不成立则调整方案 |
| M1（1–2 周） | 通知监听 + 微信消息解析 + 悬浮球出现/消失 | 来消息→弹球→消失 |
| M2（1 周） | 回复面板 UI + 键盘适配 + 消息摘要 | 面板体验顺手 |
| M3（1–2 周） | 无障碍发送链路（切走→注入→发送→返回） | 文章原位返回 ✅（核心验收） |
| M4（打磨） | 自动返回时机、防误触、ROM 权限引导、录屏 demo | 录一段"阅读→回复→原位返回"视频 |

**M0 事实验证（开工前必做）：**
1. 主力机安卓版本与 ROM（决定权限引导复杂度）；
2. 微信"切走回复→按返回"后，公众号文章**位置是否保留**（决定"原位返回"体验是否成立）；
3. 通知里能否拿到聊天对象名与消息文本（决定解析器写法）。

## 10. 简历卖点（把这个项目讲成故事）

- **系统能力整合**：一个应用串联通知监听、悬浮窗、无障碍三大系统级 API，纯外部辅助、零注入零改包；
- **对抗性适配**：微信 UI 节点无公开文档，靠 className/text 多策略定位输入框与发送按钮，并设计兜底降级；
- **体验工程**：以"阅读中断最小化"为目标做交互（气泡触发条件、自动返回时序、防误触）；
- **工程规范**：模块化包结构（UI / 服务 / 核心操作器分离），无障碍发送逻辑收敛为单一模块便于演进。
- 演示素材：录屏"沉浸阅读中完成一次回复且文章原位返回"。

## 11. 后续可扩展（非 MVP，先不做）

- "稍后回复"队列：把打扰转化为排队（成本低、价值高，v2 首选）；
- 快捷短语 / 语音转文字输入；
- PC 端浏览器扩展（微信网页版 + 文章并排）；
- 若商业化：隐私政策、无障碍用途声明、商店分发合规。

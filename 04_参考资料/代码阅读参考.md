# 代码阅读参考

> 用途：遇到"要读代码"的场景，先来这儿找对应的入手方式。
> **场景不同，读法完全不同 —— 用"读题解"的方法去读大项目，一定卡死。**
> 建立：2026-10-14

---

## 零、四招通用（任何场景都能用）

### 招 1 · 骨架法：先盖住内层，只读外层

嵌套循环读不顺，**不是因为你笨，是因为你在同时跟踪两个变量**。

```
result = [[1]]
for i in range(1, numRows):      ← 重复 numRows-1 次，每次造一行
    prev = result[-1]
    ...                          ← 盖住！先当它不存在
    result.append([1] + mid + [1])
return result
```

**先用三行读懂外层**（"每轮取最后一行、算点东西、接一行新的上去"），再展开 `...`。

展开时，**先只看黑盒的"输入和输出"**（吃 `prev`、吐 `mid`），最后才看里面。

> 类比：读长句子先找主谓宾，再补修饰成分。没人一上来就读每个形容词。

### 招 2 · 变量状态表：循环读不懂，就手写表跟踪

| 轮 | left | right | k | 做了什么 |
|---|---|---|---|---|
| 1 | 0 | 4 | 4 | 放 100 到 4 号格 |
| 2 | 0 | 3 | 3 | 放 16 到 3 号格 |

**在脑子里"跑"多个变量几乎必崩，写在纸上就不崩。** 写三行就懂了。

### 招 3 · 给变量在脑子里改个中文角色名

`i` `j` `k` `n` `tmp` `res` —— 这些名字**不含任何信息**。读的时候在心里换掉：

- `i` → "第几行" ｜ `j` → "这一行的第几个" ｜ `k` → "下一个要填的格子"
- `n` → "还剩几个" ｜ `prev` → "上一行" ｜ `res` → "攒结果的容器"

**变量名读不懂 → 代码一定读不懂。** 这一条能救掉一半的"读不顺"。

### 招 4 · 读之前先问三个问题

不要从头往下扫，先问：

1. **它要产出什么？**（返回什么 / 改哪个数组）
2. **输入是什么？**
3. **从输入走到输出，它必须"记住"什么？** → **那就是变量存在的意义**

带着问题读，比逐行扫描快十倍。

## 一、读一道题的题解（20~50 行）

| | |
|---|---|
| **入口** | **函数签名 + 返回值** —— 先确认"吃什么、吐什么"，再看里面 |
| **读到什么程度算够** | 能说出"每个变量代表什么 + 循环在重复什么" ⇒ **然后关掉重写** |
| **常见坑** | ① 逐字翻译每一行（翻译完还是不会写）；② 看到不认识的语法就停下 —— **先跳过，抓数据流向，语法最后查** |

> 题解只有 20 行，但它**信息密度极高** —— 每一行都在表达一个决定。所以不能扫，得逐行问"为什么是它"。

---

## 二、读自己的旧代码

| | |
|---|---|
| **入口** | **先看日志的「卡点 / 收获」栏，再看代码** —— 日志告诉你当时为什么那么写 |
| **读到什么程度算够** | 能复述核心思路 + 能说出"当时踩的坑现在还在不在" |
| **常见坑** | 以为自己还记得；直接看代码会被"我当时的写法"带偏（尤其是错的写法） |

> 这是**间隔复习**的主场：隔几天读自己的旧代码，比读新题解有用。

---

## 三、读中型项目（一个仓库，几十个文件）

| | |
|---|---|
| **入口** | `README` → **目录树** → **入口文件**（`index` / `main` / `app`）→ 依赖清单（`package.json` / `requirements.txt`） |
| **读到什么程度算够** | **能用一句话说出每个目录在干什么** —— 这一步做完，你已经"读"完 80% |
| **常见坑** | **按文件顺序横着读**（A 文件读一半跳到 B，最后什么都没留下） |

---

## 四、读大型真实项目 / 多包仓库（如 `04_参考资料/project01` 的 pi）

**核心原则：永远不要"读完"，只读"一条线"。**

想读完几百个文件 = 想放弃。你只需要回答**一个具体问题**，然后把跟它有关的那条线追完。

**四步：**

1. **先读"地图"，一行实现都别看**
   - README / **docs 目录** / 目录结构 / 入口文件 / package.json
   - 🔧 pi 的现成福利：`packages/coding-agent/docs/` 下的 md（`harness.md`、`sessions.md`、`skills.md`、`providers.md`…）**就是地图，先读它再读 `src/`**

2. **选一条主线，纵向追**
   - 别按文件顺序读。选一件具体的事（"我发一句话，agent 怎么回我"），顺着它把所有相关文件串起来
   - **追的时候记调用链**（谁调用谁）—— 这就是你的进度条

3. **画图（合上代码画）**
   - 哪个文件调用哪个文件、数据长什么样
   - **画不出来 = 没读懂**

4. **终点不是"读完"，是"能改一行并知道会发生什么"**
   - 自检句：**"如果我要加一个工具，得动哪几个文件？"**
   - 能回答 = 真懂了；答不出 = 还在漫游

| | |
|---|---|
| **常见坑** | 想读完；横着扫；被抽象层（接口 / 事件 / 依赖注入）吓住 |

## 五、读框架 / 库的源码（API 你已经在用）

| | |
|---|---|
| **入口** | **从"你自己代码里调用它的那一行"出发，反向往里追** |
| **读到什么程度算够** | 能说出"我这一行调用，它内部到底做了什么" |
| **常见坑** | 从仓库顶部开始读（那是给维护者看的顺序，不是给你的） |

> **优势**：你已经在用它了 —— 有"使用经验"当对照物，理解会快得多。

---

## 六、读不熟悉语言的代码

| | |
|---|---|
| **入口** | **先抓"数据的形状"**：TS 的 `interface` / `type`、C 的 `struct`、Python 的类字段 |
| **读到什么程度算够** | 能说出"数据从哪来、到哪去" |
| **常见坑** | **卡在语法上** —— 一停就再也起不来 |

> **TS 项目专属**：先读类型定义，再读实现。**类型定义 = 数据的形状**，实现只是"怎么加工"。类型读懂了，实现基本能猜到。

---

## 七、只想改一小块（拿来主义）

| | |
|---|---|
| **入口** | **先找边界** —— 哪几行是你要的？它依赖了外面的什么？ |
| **读到什么程度算够** | 那一小块能**独立跑起来** |
| **常见坑** | 整块复制，带着一堆你用不到的依赖 |

---

## 附 A · 最狠的一条

> **只读你"已经写过一遍"的东西。**

有对照物才读得进去。先自己写一遍，再去读别人怎么写 —— 这时候你读的每一条都是"**那我呢？**"。

**完全没见过的东西，读了也白读。**

（所以：写 `pi_ai` → 读 pi，是正确顺序；反过来不成立。）

---

## 附 B · 读代码的终点：能"改动它"

**不是"读完"，不是"看懂"，是"能改一行并预知会发生什么"。**

- 读完一道题解 → 终点是**关掉重写**
- 读完一个模块 → 终点是**加一个功能 / 改一个行为**
- 读完一个项目 → 终点是**能说出"要改 X 得动哪几个文件"**

---

## 附 C · 心态两条

1. **读别人的代码，不要求每行都懂。** 目标是"能说出它大概怎么干、关键变量各代表什么"。
2. **缩进 = 归属。** 看不懂某一行，先往上找它的"东家"（最近的 `for` / `if` / `def`）。

## 附 D · 一张速查表

| 场景 | 入口 | 读到什么程度算够 |
|---|---|---|
| 题解 | 函数签名 + 返回值 | 能讲清变量 → **关掉重写** |
| 自己的旧代码 | **日志的卡点栏** | 能复述思路 + 看出坑还在不在 |
| 中型项目 | README → 目录树 → 入口 | 每个目录一句话 |
| 大型 / 多包仓库 | **docs 当地图** → 追一条主线 | 能回答"改 X 动哪几个文件" |
| 库 / 框架 | **从自己调用它的那一行**反向追 | 能说出"我这一行内部做了什么" |
| 陌生语言 | **先读类型 / 数据结构** | 能说出数据从哪到哪 |
| 拿来改一小块 | **先划边界** | 那一小块能独立跑 |
